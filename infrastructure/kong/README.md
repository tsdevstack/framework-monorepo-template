# Kong Gateway Image

This folder is the build context of the local Kong gateway image. Most of it is generated by tsdevstack: don't edit the generated files, your changes are overwritten.

## First run on a fresh clone

Run this before `docker compose up`:

```bash
npx tsdevstack sync
```

`sync` (or `npx tsdevstack generate-kong`) writes the build context below. The `kong-plugins/` and `declarative/` folders are gitignored, so a fresh clone does not have them and the gateway image cannot build until one of these commands has run. `sync` also starts the stack with `docker compose up --build`, which rebuilds the gateway image.

## What's in here

| Path | Generated | Committed | What it is |
|------|-----------|-----------|------------|
| `Dockerfile` | Yes | Yes | The Kong image definition |
| `.dockerignore` | Yes | Yes | Sends only the Dockerfile, `kong-plugins/` and `declarative/` to Docker |
| `kong-plugins/` | Yes | No | Copies of the framework plugins and of your `kong-plugins/` folder at the project root |
| `declarative/` | Yes | No | Empty locally (the config is mounted); cloud builds bake `kong.yml` in here |
| `{env}/kong.yml` | Yes (`infra:generate-kong`) | Yes | Cloud config per environment, with `${SECRET}` placeholders |
| `README.md` | No | Yes | This file |

## The image

The same Dockerfile is used locally and in the cloud (`infra:build-kong` writes it into its own build context). It contains:

- `kong:3.8.0`
- the OIDC plugin (`kong-oidc-v3` with `lua-resty-openidc`) for JWT validation through the auth service's JWKS; installed from GitHub at pinned versions because luarocks cannot install it on Kong 3.8
- the tsdevstack plugins: `tsdevstack-strip-identity` (removes identity headers sent by clients, before any auth plugin runs), `tsdevstack-api-key` (checks partner API keys against Redis) and `tsdevstack-api-prefix` (removes `/api` from partner API requests)
- every plugin in your `kong-plugins/` folder
- `KONG_PLUGINS` listing all of them
- nginx shared memory caches for the OIDC plugin (`lua_shared_dict discovery` and `jwks`, in `/etc/kong/tsdevstack-nginx-http.conf`, included through `KONG_NGINX_HTTP_INCLUDE`), so Kong fetches the auth service's discovery document and signing keys once instead of on every JWT request

The image defaults are the cloud settings (proxy on 8080, Admin API off, config baked in). The `gateway` service in `docker-compose.yml` overrides them for local development: proxy on 8000, Admin API on 8001, `kong.yml` from the project root mounted at `/kong/kong.yml`, and no request body size limit.

## Custom plugins

Put your own Lua plugins in `kong-plugins/` at the project root (not in this folder), one folder per plugin:

```
kong-plugins/
└── my-plugin/
    ├── handler.lua
    └── schema.lua
```

- The folder name is the plugin name: lowercase letters, digits, `-` or `_`, matching the name in `schema.lua`.
- `handler.lua` and `schema.lua` are required.
- Names used by Kong's bundled plugins, the OIDC plugin or the tsdevstack plugins are rejected.
- Enable the plugin in `kong.user.yml` like any other plugin.
- Commit `kong-plugins/`. The same plugins reach the local image (`npx tsdevstack sync`) and the cloud image (`infra:build-kong`).

If you edited this Dockerfile by hand before it was generated, move your plugins into `kong-plugins/`; other custom build steps are not carried over.

## Rebuilding

- Config change only: `kong.user.yml` edits need `npx tsdevstack generate-kong`, then `docker compose restart gateway`. New or changed endpoints also need fresh OpenAPI docs first (`npm run docs:generate`); `npx tsdevstack sync` does both.
- Plugin or Dockerfile change: `npx tsdevstack sync`, or `docker compose up -d --build gateway`. A plain `docker compose up` keeps the old image.
- Cloud: `npx tsdevstack infra:generate-kong --env <env>`, `infra:build-kong`, `infra:deploy-kong` (the full `infra:deploy` runs all three).
